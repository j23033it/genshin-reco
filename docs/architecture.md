# アーキテクチャ方針

## 製品の位置づけ

本アプリはDPS計算機でも全ゲーム情報のローカル図鑑でもない。ユーザーが指定した4人だけを会話から都度調査し、根拠付きの編成カードとして蓄積するアプリである。

初期状態は空でよい。調査に成功した情報だけを保存し、次回以降の表示と再調査へ使う。

## 信頼境界

- Rendererは会話入力、進捗、保存一覧、画像付き結果の表示に限定する。
- 任意コマンド、任意ファイル、SQLite、認証情報、アクセストークン、任意URL取得をRendererへ公開しない。
- Codexは探索、抽出、構造化のみ担当する。
- Rust Trusted Coreが会話状態、4人制約、URL検証、構造化出力検証、キャンセル、永続化を担当する。
- 外部ページ本文とCodex出力は未信頼データとして扱い、HTMLやコマンドとして実行しない。

## 採用技術

- デスクトップ: Tauri v2
- Renderer: React + TypeScript + Vite
- UI: Tailwind CSS + Base UI
- Trusted Core: Rust
- 永続化: SQLite
- Codex接続: `codex app-server`のstdio JSONL
- 保存: 会話、完成編成、キャラクター・武器・聖遺物ごとの再利用知識を分離して保持

## オンデマンド調査

- 会話履歴はアプリDBを正本にする。Codexの履歴保存へ依存しない。
- 受付と本調査は一時App Serverスレッドで行い、各回の完全な会話または4人条件を渡す。
- 受付はWebを使わず、4人の名前と任意の武器・凸・精錬だけを抽出する。
- 受付は推論量を`medium`にし、スレッド設定でもWeb検索を無効にする。受付と本調査のモデルは`gpt-6-sol`を使う。本調査は同じ一時スレッド内で、資料収集を`medium`、編成・数値の検討を`low`の基本2ターンで行う。両ターンともFastを使う。ホストが4人分の検索文を用意し、独立した検索と本文取得をまとめる。資料収集では対象名・数値と条件の短い要約・出典URLを整理する。ホストは未閲覧の出典が付いた要約を確認事項へ戻し、有効な要約と正規化した閲覧済みURL一覧を次のターンへ明示的に渡す。不足や矛盾がなければ同じ本文を読み直さない。
- 検索結果の量は`context_size = "low"`にする。保存済み出典の本文を先に開き、不足するキャラクターのビルドだけを2〜4件ずつまとめて検索する。初回の本文確認は各対象1〜2件を目安にし、そこで読めない武器・天賦・命ノ星座の効果だけを追加検索する。同じ武器の検索文は重複を除き、本文を共有して精錬ごとの条件を確認する。根拠不足・取得失敗・矛盾がある場合は件数に縛られず追加確認する。
- 資料収集で、主参照ステータスに関係するLv90基礎値・突破値、爆発の必要エネルギー、指定武器のLv90値・指定精錬効果・発動条件、採用候補の聖遺物効果を揃える。同じ本文の関連する数値はまとめ、要約の件数を増やす分割や指定外の凸・精錬の調査を求めない。最終検討は採用するビルドの数値・成立条件に関わる不足だけを追加確認する。
- ビルドのおすすめと固定値を読む目的を分ける。必要エネルギーは原神WikiまたはHoYoWikiの該当天賦表、基礎値・武器値はLv90列、効果は原文・精錬表で確認するよう求める。サイトや記事を追加しただけで矛盾が自動解消される仕組みではない。
- 育成水準が未指定ならLv90・聖遺物最大強化を共通の前提として一度だけ説明する。確定装備から計算できる最低値を目標範囲の下限が下回らないよう求める。戦闘中の効果と発動条件は残し、同じ前提の繰り返しや適用しない効果の列挙を省く。速度改善は指示の変更であり、5分以内や数値の正確さを保証する仕組みではない。
- 検索結果の要約だけを根拠にせず、本文を取得する`live`を維持する。`cached`への切り替えや取得本文の短時間保存は、今回の本文確認と再調査の約束を満たすかを別途検証してから検討する。検索設定の根拠は[OpenAIの公式設定資料](https://learn.chatgpt.com/docs/config-file/config-reference)を参照する。
- App Serverの初期設定は`service_tier = "default"`、`fast_mode = false`とする。編成調査のスレッドだけ`service_tier = "fast"`、`features.fast_mode = true`で上書きし、開始応答のモデルと`serviceTier = priority`（または`fast`）を確認する。受付はWebなし・通常モードのまま扱う。アプリ専用ホーム以外の設定は変更しない。各ターンの標準エラー出力に経過時間、Web完了イベント数、閲覧URLの記録数、異なる閲覧URL数を記録する。ページ内検索や複数URLを含む通知も数えるため、実際の通信回数や全文の再取得回数ではない。並列実行や時間短縮を保証する値でもない。検索文・本文・ユーザー入力はこの記録に含めない。
- App Serverの初期化・スレッド開始・ターン開始の応答は60秒まで待つ。調査は対象ターンの進捗通知が10分途絶えた場合、または全体で30分経過した場合に打ち切る。タイムアウトには待機した処理または停止理由を表示する。
- 通知で完了待機を起こす。キャンセル時の中断確認は5秒までとし、専用プロセスを終了する。成功した専用調査は購読解除の応答を待たずにプロセスを終了し、後片付けの遅延で結果を失わせない。
- 本調査はCodexのWeb検索を使い、原神Wiki、Game8、HoYoWiki、GameWithの個別本文ページだけを根拠にする。資料収集と最終検討の実際の本文閲覧イベントを使って出力URLを確認する。最終検討の出力Schemaでは出典URLを収集時に開いた個別本文URLの列挙値と`null`に制限する。検索結果や未閲覧の資料を根拠にせず、URLを推測で生成しないよう指示する。検討中に追加で開いた資料はページを特定できるタイトルと`null`で保留する。保留またはURL不一致があれば、両ターンで開いたURLだけを選択肢にした`medium`の確定ターンを一度だけ追加する。AIは出典の位置と修正URLだけを返し、数値・説明・出典の件数と順番はホストが保持する。未閲覧URL・重複指定・未修正・対応不明・修正中の再検索は拒否する。公開する編成データのURLは従来どおり文字列とし、未確定の出典を削除して成功扱いにはしない。URLの閲覧記録との一致は、数値の読み取りやページと主張の対応を保証しない。確定も含めた調査全体の上限は30分とする。
- 2026年9月27日、検索量を`low`にして件数の目安だけを指示した実調査は、資料収集69.5秒、最終検討1579.7秒だった。検討ターンのWeb完了通知25件には閲覧URLの記録102件、異なるURL20件があり、最後は黒纓槍の出典URLが閲覧記録と一致せず失敗した。この結果を受けて、要約と閲覧済みURLの明示的な引き継ぎ、URLだけの一度の修正を追加した。使用CLIは`0.158.0-alpha.2.1`で、前日の結果との時間差から変更の効果を断定しない。
- 同日の改修後、資料整理とURL修正だけの実確認は115.6秒で成功した。資料整理は111.6秒、Web完了通知5件、本文9ページから出典付き要約31件と不足事項9件を引き継げた。URL転記ミスを意図的に付けた確認用データは3.4秒で修正でき、追加のWeb実行はなく、他のデータを保持した。これは4人の最終検討を含む全体の計測ではなく、改修後の全体の時間短縮は未確認である。
- 2026年9月26日の同一4人・指定武器での実調査では、2ターン方式は13分3秒で13件の根拠検査まで成功した。比較した1ターン方式は約16分半後に、本文取得を確認できない出典URLの検査で失敗した。これは通常モードでの1回の比較であり、編成やサービスの応答状態によって所要時間は変わる。
- 画像URLはホストが同梱の `public/data/catalog.json` から名前を照合して設定する。キャラクター・武器はそれぞれの画像、聖遺物は花の画像を使い、AIには画像の検索を依頼しない。
- 保存時と既存結果・一覧の読み込み時に同じ画像照合を行う。画像がnullの保存済み結果も再調査せず表示できる。空白・全半角の括弧、精錬や4セットの表記は吸収する。名前が未登録、複数候補や2+2セットで画像を一つに決められない場合はnullとし、取得に失敗した場合とともにUIが文字の代替表示を使う。
- 各メンバーは会心・ダメージバフだけでなく、攻撃力、HP、防御力、元素熟知、基礎攻撃力など役割の計算元となる主参照ステータスを1件以上持つ。
- 目標ステータスの名前・値が空または空白だけなら、保存前の検証で拒否する。指示では実在する目標を2〜5件選ぶよう求め、必要件数を空の項目で埋めない。
- 入力で指定した4人・武器・命ノ星座が完成結果と一致するかを調査完了時と保存前に検証する。資料要約に指定外の凸の説明があっても、ユーザー指定を上書きしない。無凸・0凸・C0など既存の表記も受理する。
- 再調査は同じ会話IDと編成IDを使い、直前の保存結果を成功時に差し替える。
- 新しい会話では、同じ4人・武器・命ノ星座・精錬、同梱カタログ、調査ルールに一致する直近7日以内の成功結果を再利用する。4人の並び順と編成名は再利用判定に含めず、結果は現在の入力順へ並べ直す。未指定と具体的な指定は区別する。
- 調査ルールの識別子は、調査の指示、モデルと推論設定、スレッドのFast設定、出力Schema、出典の選択方式とルールから生成する。変更前の完成結果を新しいルールの成功結果として再利用しない。完成結果の再利用データは`on_demand_knowledge`の`entity_type = team_research`として、完成編成と同じトランザクションで保存する。再利用時に元の調査日時を更新しない。
- 条件が一致しないときは、直近7日以内かつ同じゲーム版のキャラクター・武器の保存済み出典を最大12件まで渡す。別編成の目標値は渡さず、Codexが個別本文を開いて確認し直す。従来の本文閲覧イベントとURL検証は省略しない。
- 保存済み編成からの再調査は完成結果の再利用を省き、Webで確認し直す。期限切れ・壊れた再利用データは通常調査へ戻す。

GameWith追加時の比較では、資料収集各2回の平均は追加前128.3秒・追加後117.3秒だった。完成編成までの追加前1回は根拠URL検査で失敗し、追加後1回は929.6秒で17件の出典確認まで成功した。GameWith由来の9件を根拠として利用できたため対象へ採用したが、全体の高速化や精度・成功率の改善は断定しない。[比較条件、数値確認、残る限界](research/gamewith-2026-09-27/comparison.md)を参照する。

2026年9月28日、Sol・収集medium・検討low・Fastと出典URLの選択制限を実装した。新規ホームでの実調査は273.0秒で出典20件の検査まで成功し、追加閲覧した資料のURL確定にも3.7秒で成功した。[自動検査、実測、数値の抜き取り確認と限界](research/source-selection-2026-09-28/verification.md)を参照する。

## 保存境界

- `on_demand_research_sessions`: 会話、4人の指定、状態、エラー
- `researched_teams`: UI表示に必要な完成編成
- `on_demand_knowledge`: キャラクター、武器、聖遺物単位の再利用可能な調査断片

完成編成と再利用知識は同じSQLiteトランザクションで保存する。途中失敗した調査を保存一覧へ追加しない。

## 仕様の優先順位

1. ユーザーの現在の依頼
2. 「要件設計レビュー」チャットの最終レビュー
3. 添付設計資料ZIP
4. 添付ゲームカタログ

最終レビューと原設計が衝突する場合は最終レビューを優先する。

## スターレイルのゲーム境界と固定遺物

オンデマンド調査の `game` は `genshin` / `star_rail`。会話、受付条件、結果、一覧、進捗に引き継ぎ、作成済み会話のゲーム変更は保存層でも拒否する。SQLite v6 の移行は、旧会話と旧編成 JSON に欠けている `game` だけを `genshin` として追加する。ID、タイトル、出典、日時は変更しない。既存のバックアップ方式を維持し、再実行は重複を作らない。

互換契約の `weapon` / `constellation` / `refinement` はスターレイルでは光円錐 / 星魂 / 重畳を表す。ゲーム固有の固定条件は `relics` に分離し、トンネルは null / `four_piece` / `two_plus_two`、オーナメントは null / 正式名称とする。2＋2は異なるセット名二つを持ち、部位や実物数値を保存しない。Rust の入力検証は所属カテゴリ、運命、名称、個数を確認する。空欄と0凸は別条件で、光円錐解除時に重畳も解除する。

同時編成できない別形態はカタログの `exclusiveGroup` を共有し、受付と結果検査で拒否する。資料収集の要約、出典選択Schema、URL修正、最終出典検査には同じゲーム識別を渡し、別ゲームの資料を最終検討へ引き継がない。WIKIWIKIの分類一覧・メニューも本文候補から除く。取得イベントに失敗・空結果・最終URLがある場合はその情報を優先し、要求URLだけで取得失敗を閲覧済みに戻さない。イベントに最終URLやHTTP結果がない場合のリダイレクト・本文確認はモデルの閲覧に依存するため、実Webの確認記録が別途必要になる。

結果の `starRail` は星魂、光円錐、重畳、構造化したトンネルとオーナメント、セット別の理由・発動条件・出典を持つ。`teamReasoning` は編成全体の採用理由と支援分担を説明する。画像はホストが各カテゴリのカタログから設定する。実測値を入力していないため、条件成立を保証しない。固定／提案表示は結果の自己申告ではなく `inputMembers` から決める。旧記録で入力スナップショットがない場合、スターレイルの提案値を固定入力として復元しない。

入力条件は会話に保存し、成功結果にも `inputMembers` として別保存する。再調査では会話の指定を復元し、未指定を結果の提案値に変換しない。失敗やキャンセルでは前回成功した結果とキャッシュを更新しない。調査完了時と保存直前にゲーム・メンバー・星魂・光円錐・重畳・固定セット・セット別根拠を検証する。根拠URLの本文閲覧履歴は App Server で検証するが、主張の意味と本文の対応を機械的に保証するものではない。

再利用キーはゲーム、キャラに結び付いた固定トンネル／オーナメント、2＋2の順序正規化、従来の全条件・モデル・指示・Schema・出典ルール・カタログを含む。別キャラへ指定が移ると別キーになる。スターレイルの調査断片は `star_rail:` の entity_type 名前空間へ分け、旧原神の知識行と衝突させない。カタログと調査結果のゲーム版が異なる場合は完全一致再利用を登録しない。明示的な再調査は常にWeb確認へ進む。

画面はゲームごとの会話・編成一覧・入力途中の文と条件を独立して保持する。処理中は理由を表示して切替を無効化し、セッションIDとゲームの両方が一致する進捗だけを適用する。未登録の古い固定名称を消さず再選択が必要な状態を示す。
